Cloud reliability · Python / Docker / Terraform

Make recovery observable.

Azure Recovery Lab

The problem

An application can become unhealthy while its process stays alive. A recovery claim needs more than a healthy screenshot.

The solution

A Python service with health probes, process identity and a controlled failure, deployed with Terraform and short lived GitHub OIDC authentication.

43.158 sOne controlled Azure recovery trial.
CLI start to completed healthy response, including setup and polling.

Same replica, new healthy process. Azure performed the restart. Single replica, visible downtime, no SLA. Temporary lab resources and scoped permissions were independently verified removed. Final billing remains unposted.

Code & setup ↗Inspect evidence ↗
Engineering decision Why one replica and a fault bound to one boot?

One replica makes downtime visible instead of masking it behind another instance. The fault marks only the selected boot unhealthy; it does not request a restart. Platform events and a different healthy boot establish recovery in the same replica, and the new process does not inherit the old failure marker. This proves a controlled recovery mechanism, not automatic repair of arbitrary application bugs.

Cited Change Analyzer

The problem

“This document changed” is not enough. Reviewers need to find the exact passage behind each finding.

The solution

An installable tool for local TXT and selectable text PDF comparisons, with exact citation spans, PDF page provenance and exportable reports. No Node, Docker or API key is needed for local comparison.

Verification34 synthetic document regression checks, released package checks and separate small live provider smoke checks.

Optional AI uses your own key after explicit consent. Regression checks are not a general accuracy or legal reliability claim.

Engineering decision Why separate source alignment from AI explanation?

Deterministic comparison and exact source mapping remain usable without a provider. Optional AI explanation is a separate, consented step with bounded source windows. If the provider rejects a request or coverage is incomplete, local findings remain available. Agent reviewed benchmark results are labeled separately from local document checks and human legal assessment.

Service Intake Workbench

The problem

A request without an owner or history gets lost. Repeated partner events can create duplicate work.

The solution

A deployed application for public intake, staff assignment, work, resolution and an activity trail. Signed partner ingestion demonstrates replay safe processing.

VerificationAPI and database integration checks cover validation, workspace isolation, workflow transitions, signatures and concurrent replay.

Use invented information only. Demo entry grants a synthetic dispatcher role, not production authentication. No real customer messages are sent.

Try the demo ↗Code & setup ↗Integration checks ↗
Engineering decision What happens when the same webhook arrives twice?

A transaction advisory lock in PostgreSQL serializes the replay key. Concurrent copies resolve to one request rather than racing to create duplicates. Workflow changes and their activity events commit in the same transaction, keeping the displayed history aligned with the saved state.

Closeout: Proof of Handoff

The problem

Stale or mislinked evidence can make unresolved work appear ready for handoff.

The solution

A responsive frontend that stages an exact proposal, requires a visible human decision and applies the approved payload once. Remaining exceptions stay visible.

VerificationBrowser regression exercises production handlers, approval and replay guards, reset, keyboard behavior and responsive layouts.

Ordinary browsers show Preview mode. Full application needs a compatible WebMCP surface. Static synthetic frontend, not a real construction approval backend.

Open preview ↗Watch walkthrough ↗Verification ↗
Engineering decision Why is “stage” different from “apply”?

Staging a proposal does not increase readiness. The approval binds the exact payload, evidence and current state to the page generation and a one use token. Changed context or a consumed token rejects the application. One accepted item can advance while the remaining exceptions still keep handoff blocked.
